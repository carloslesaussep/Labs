	-Avro:  
		Structure: Structured / Semi-structured (JSON-defined schema + binary data)
		Readability: Human-readable schema (.avsc) but unreadable data (.avro)
		Size: Compact binary, very efficient compression
		Scheme base: Row based
		
	-Parquet:  
		Structure: Structured
		Readability: Unreadable (binary format)
		Size: Extremely light, highly compressed
		Scheme base: Column based 
		
- Q3.2
Considering that analytic systems are used for larger data files and numbers rather than multiple fast paced light file based reads, becasuse on column based formates data of the exact same type (e.g. customer_id, customer_name etc.) are stored in a sequence one right to another in a column, compression algorithms work exceptionally well, which provide storage and processing benefits.

- Q3.3
Readability: While JSON is text based and human readable where data is stored as key values, AVRO is a binary encoded format where only the schema can be considered readable due to being stored in JSON format, the separate file type present in AVRO where the whole content is stored is non readable.

Size and storage efficiency:  While JSON is heavy due to every single record repeating the keys, AVRO is compact, just repeating the keys the needed amount of times due to the schema being stored in raw format and having all the weight of the file (real content and values) stored in binary.

- Q3.4
Parquet can achieve massive storage savings and faster queries because its columnar layout groups identical data types together. This minimizes disk Input Output bottlenecks and allows more data to fit into memory caches for high-speed analytical processing.

- Q4.1
Orders table: Partition by order_date (monthly or yearly) to isolate time periods so queries skip scanning irrelevant historical data

Clickstream data: Partition by event_timestamp (daily or monthly) to handle high-volume data growth and easily drop old logs

- Q4.2
Customer lookups: Create a composite index on customer_id and email for fast single-row retrieval during logins or searches

Order filtering: Create a composite index on (customer_id, order_date) to speed up filtered time-range searches per user

Joins: Index foreign key columns like customer_id and product_id to optimize merge operations across tables

- Q4.3
Write Penalty : Every write forces the database to update all related indexes, slowing down data ingestion

Storage Overhead: Indexes consume extra disk space, which can accumulate quickly on large tables.

Low Cardinality: Indexing columns with few unique values  is ignored by the query optimizer and wastes resources
